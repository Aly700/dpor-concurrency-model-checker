# ADR 0017: PSO Address Buffers and Cross-Model Inclusion

## Status

Accepted.

## Context

ADR 0015 added TSO as an explicit alternative to the default SC semantics.
TSO delays plain writes in one FIFO per thread, so it relaxes store-to-load
order while preserving store-to-store order. Partial store order (PSO) is the
next member of that family: stores to one address remain ordered, but stores to
different addresses may become visible in either order.

That last sentence creates a scheduler problem, not just a buffer-layout
change. After one thread enqueues `data=1` and `flag=1`, both `flush(data)` and
`flush(flag)` must be enabled. If exploration chooses only a canonical address,
or applies the source-program rule that all same-thread transitions are ordered,
the model never reaches `flush(flag); read(flag); read(data); flush(data)`.
Such an implementation calls itself PSO but behaves like TSO on the message-
passing discriminator.

The change must preserve existing SC and TSO behavior, deterministic numeric
schedules, exact replay, visibility-point race accounting, and exact lasso
proofs. It also introduces a different kind of verification gate: behavior
inclusion between memory models, rather than reduced-vs-naive agreement within
one model.

## Decision

### Buffer representation and value semantics

TSO keeps its existing `deque<(address, value)>` per thread unchanged. PSO has
a separate `map<address, deque<value>>` per thread. The map gives canonical
lexicographic address order; each deque is the address's FIFO. Empty queues are
erased, so absence is the only representation of an address with no pending
stores.

A PSO plain write appends to its address queue. One internal flush transition
is enabled for every `(thread, address)` whose queue is nonempty. It commits
only that queue's oldest value. Two writes to one address therefore cannot
reorder, while different-address queues may drain in either order. A plain load
forwards the newest value from its own same-address queue, otherwise it reads
shared memory. Loads remain source-program actions and PSO does not relax their
order.

The global visibility point is the flush, exactly as under TSO. Enqueueing does
not update shared memory or plain-write race metadata. The flushing thread
ticks its clock for the internal step, and race bookkeeping records the flush
endpoint. Forwarded reads are still conservatively recorded as plain reads, so
same-address dependence remains visible to DPOR.

A started thread is finished only when its source pc is done and every buffer
owned by the selected model is empty. A pending queue always enables its flush,
so buffered completion alone cannot be a deadlock.

### Numeric schedule encoding and exact replay

`ScheduleStep` remains numeric. Source actions are still two numbers:

```text
thread action_index
```

TSO flushes remain the same two-number sentinel using
`kFlushActionIndex == UINT32_MAX`. A PSO flush uses the same sentinel plus a
third number:

```text
thread 4294967295 canonical_address_id
```

The address ID is the zero-based index in the lexicographically sorted set of
nonempty program action addresses. It is fixed for the program, independent of
the current buffer contents, and therefore stable across exploration, report
rendering, and replay. Existing SC/TSO schedule files and report blocks remain
unchanged.

Replay accepts the sentinel under TSO only without an address ID and only when
the single FIFO is nonempty. Under PSO it requires an ID, maps it through the
canonical program table, and requires that exact address queue to be nonempty
at that step. It rejects omitted IDs, IDs for a different or absent queue,
address IDs attached to source actions, and every flush under SC. This is why
one unqualified sentinel was not reused for all PSO flushes: it would identify
that *some* queue drains but would not reproduce which transition executed.

### Ordered points and the fence choice

Under both buffered models, atomics, CAS, lock, unlock, wait, signal,
broadcast, spawn, join, and `fence` are disabled until all buffers of the
executing thread are empty. For PSO, “all” means every address queue. The
operation executes normally after the drain; it does not perform a hidden
bulk commit.

The IR intentionally keeps one full `fence`. It restores the same simple
contract in TSO and PSO: all earlier plain writes are globally visible before
the next source action. A separate store-only `sfence` would currently have no
additional observable value because the IR does not model load buffers or
load reordering. Adding it would expand the language, schedule reasoning, and
gallery without distinguishing another modeled behavior. It remains possible
future work if the IR grows weaker load semantics.

### Same-thread, different-address flushes

At the action-effect level, `flush(x by T)` and `flush(y by T)` commute when
`x != y`: they pop different queues, update different cells and race metadata,
and leave the same direct state after both execute. The transition predicate
therefore recognizes them as independent even though they carry the same
source thread ID. Flushes of the same address remain dependent and FIFO exposes
only one such transition at a time.

The existing trace-DPOR algorithm has a separate source-order assumption: it
never dynamically reverses two transitions with the same thread ID. Relying on
ordinary independence here would be unsound. Starting with `flush(data)` and
discarding the commuting `flush(flag)` choice represents the final state after
both drains, but it does not represent schedules where another thread runs
between them. The MP failure needs exactly that middle observation.

PSO therefore adds a conservative persistent-set rule. Whenever a flush for a
thread is selected into a node's initial backtrack set, every co-enabled flush
of another address owned by that same thread is inserted as a sibling choice,
even though the pair's direct effects commute. Each address-tagged flush is
already a distinct key in the node's enabled-transition map. Both branches are
therefore executed, and ordinary cross-thread dependence can place observers
between the drains. The node does not emit one canonical flush and hope that
same-thread dynamic backtracking reverses it later.

This rule is deliberately conservative. It can explore more representatives
than an algorithm with virtual `(thread,address)` actors or source-DPOR wakeup
sequences, but it cannot remove a legal PSO behavior. Same-thread source action
versus flush remains dependent, so the scheduler also explores “enqueue the
next address before draining the earlier address” when both are enabled. A
flush cannot move before its enqueue because its address queue does not yet
exist. The `pso_oracle` naive-vs-DPOR sweep and the MP assertion are the
executable soundness checks for this design.

Across threads, a flush is a write-like action. `flush(x)` is dependent with a
different thread's memory operation or flush on `x`; it is independent of
different-address memory and register-only actions. These are the TSO clauses
generalized to the concrete flushed address.

### Exact lasso fingerprints

PSO fingerprints include every thread's address map in canonical map order,
then every queued value in FIFO order. The fixed address-ID table is program
metadata and need not be encoded. A litmus replay establishes shared `x=y=1`,
enters a state with one pending value in each of the `x` and `y` queues, then
enqueues and flushes once per address. The cycle closes only after both queues
return to their earlier contents. Omitting the map, either address, or FIFO
values would close the replay at an earlier prefix and make the continued
schedule invalid.

### Cross-model behavior inclusion

The modeled executions are nested:

- Every SC execution maps to a TSO execution by placing an immediate flush
  after each plain write.
- Every TSO execution maps to a PSO execution by choosing PSO address flushes
  in the same global FIFO order used by TSO. That order always respects each
  address FIFO.

Ordered points can make the same choices because the mapped execution drains
all prior writes. Store forwarding and visibility values are preserved. Race
endpoint action indexes differ for a buffered write, but bug *existence* is
preserved; the gate intentionally does not compare report identity across
models. Exact cycles map through empty-buffer boundaries, and the extra
internal clock ticks are analysis instrumentation excluded from behavioral
fingerprints.

The `model_inclusion` gate therefore asserts, independently for race,
deadlock, modeled error, assertion, and nontermination:

```text
found(SC) => found(TSO) => found(PSO)
```

It runs a deterministic two-thread corpus, fixed-seed samples, and explicit
positive fixtures for every bug kind. A program is skipped if any model reaches
the schedule cap or retains a bound-exceeded execution, because truncation
invalidates a missing-bug implication. Skips are counted and bounded. A
violation is a model bug, not a test expectation to weaken.

## Consequences

- SC remains the default and its execution path is unchanged.
- TSO retains its original buffer representation, two-number sentinel, and
  schedule/report format.
- PSO can expose store-store reordering, with MP as the defining differential.
- Full fences restore MP ordering under PSO; no new source action is added.
- PSO state and schedule keys are larger, and the conservative sibling-choice
  rule can explore more schedules than a virtual-actor DPOR design.
- `pso_litmus`, `pso_oracle`, `model_inclusion`, PSO fuzz sampling, and the
  classic gallery jointly guard semantics, reduction, replay, monotonicity,
  and user-facing behavior.
