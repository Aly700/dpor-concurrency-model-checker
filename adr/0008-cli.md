# ADR 0008: Deterministic CLI Front-End

## Status

Accepted.

## Context

The model checker library exposes a small `model::Program` IR and deterministic
exploration/replay APIs, but it did not have a user-facing text format or
command-line replay workflow. Failure reports need to remain reproducible and
byte-stable for the same inputs.

## Decision

Add a single executable named `dpor` as a consumer of `model_checker`. The CLI
parser and renderer live under `src/cli/`; they do not change the core model
semantics in `src/model/`.

The program format is line-oriented:

```text
program     ::= { blank | comment | thread | action }
thread      ::= "thread:"
action      ::= memory | mutex | condvar | join | yield
memory      ::= ("read" | "write" | "atomic_load" | "atomic_store" | "atomic_rmw") address
mutex       ::= ("lock" | "unlock") mutex
condvar     ::= "wait" condition mutex | ("signal" | "broadcast") condition
join        ::= "join" thread_id
yield       ::= "yield"
comment     ::= "#" { any character }
```

Comments begin at `#`; blank lines are ignored. Threads are numbered by
declaration order starting at zero. Parsing is strict: unknown keywords, wrong
arity, actions before `thread:`, invalid integer operands, and join targets
outside the declared thread range are parse errors. Self-join is accepted by
the parser because it is a modeled runtime error.

The executable has two subcommands:

```bash
dpor check <program.dpor> [--explorer naive|dpor] [--max-schedules N]
dpor replay <program.dpor> --schedule <schedule-file>
```

`check` defaults to `--explorer dpor`. `replay` reads a schedule file containing
whitespace-separated `thread action_index` pairs. Schedule files also allow
comments and blank lines.

## Report Contract

Reports are deterministic text with no wall-clock data and no file paths:

```text
verdict: race|deadlock|error|clean
schedules_explored: N
```

For a bug, the report then prints one details block, a human-readable trace,
and a machine-readable `schedule:` block. The machine-readable block contains
only `thread action_index` pairs after the `schedule:` marker; those lines are
accepted verbatim by `dpor replay`.

Bug precedence is `race`, then `deadlock`, then `error`, matching the public
verdict order. Details are:

- race: address plus both endpoints as `thread T action A`;
- deadlock: each blocked thread and whether it waits on a mutex, condition
  variable, or join target;
- error: endpoint and model error message.

For a reproducing bug schedule, replay must produce the same verdict and bug
details as check. `schedules_explored` may differ because replay executes one
provided schedule, while check explores a search space.

## Wait Phase Rendering

`Wait(cv, mutex)` is one IR action that may appear twice in a schedule: the
release-and-sleep phase and the later mutex reacquire phase. The CLI renderer
derives phase labels from the validated schedule itself: the first occurrence
of a wait endpoint is printed as `(sleep)`, and the second occurrence as
`(reacquire)`. A wait endpoint that is the selected modeled-error endpoint is
not phase-annotated.

No model API extension was required. The existing exploration and replay APIs
already validate schedules and expose the minimized reproducing schedule; the
duplicate wait endpoint is sufficient read-only information for rendering.

## Exit Codes

- `0`: clean check or clean replay.
- `1`: race, deadlock, or modeled error found.
- `2`: usage error, parse error, file-open error, or invalid replay schedule.

Invalid replay schedules surface the `ModelChecker::replay` exception message
on stderr.

## Consequences

The CLI is intentionally thin: it owns text parsing, flag parsing, report
rendering, examples, and golden tests, while the library remains the sole owner
of scheduling, happens-before, race, deadlock, and modeled-error semantics.
