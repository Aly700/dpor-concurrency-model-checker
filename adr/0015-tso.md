# ADR 0015: TSO Store Buffers

## Status

Accepted.

## Context

The original checker modeled sequentially consistent plain memory. To exercise
x86-style weak memory without weakening the existing SC regression bar, TSO is
an explicit `MemoryModel` selected at `ModelChecker` construction or through
the CLI. The default remains SC, and SC reports stay byte-for-byte unchanged.

ADR 0007's soundness bias still applies: over-reporting is acceptable when the
model is conservative; adding speculative happens-before edges that hide a race
is not.

## Decision

TSO adds a FIFO store buffer per thread. A source `write` enqueues
`(address, value)` into the executing thread's buffer. A new internal `flush`
transition is enabled for that same thread whenever the buffer is nonempty and
commits the oldest entry to shared memory.

Public schedules remain `ScheduleStep { thread, action_index }`. Flushes use
the reserved action index `kFlushActionIndex == UINT32_MAX`. This keeps replay
as one deterministic sequence of steps and avoids changing every public report
type into a variant. Replay validates the sentinel exactly: it is legal only
under TSO, only for a started thread, and only when that thread's buffer is
currently nonempty. CLI trace rendering prints `flush x`; the schedule block
prints the numeric sentinel so it remains parseable by the existing schedule
file grammar.

TSO ordered points are disabled while the executing thread's buffer is
nonempty: atomics, CAS, lock/unlock, wait/signal/broadcast, spawn, join, and
`fence`. The only enabled transition in that case may be one or more flushes
for that thread. This models x86 locked/synchronizing operations as implicit
drain points. `fence` is a source action; under SC it is a no-op, and under TSO
it is enabled only after the buffer is empty and has no other effect.

A thread is finished only when its pc is done and its store buffer is empty.
Because a nonempty buffer always enables a flush, buffered writes alone cannot
create deadlock.

## Race and Value Semantics

A plain write's global visibility point is its flush, so race bookkeeping runs
at flush time with the flushing thread's post-tick vector clock and the flush
schedule endpoint. Enqueue advances program order and the thread clock, but it
does not update shared memory or plain-write race metadata.

Plain reads forward from the newest same-address entry in the reading thread's
own buffer; otherwise they read shared memory. A forwarded read is still
recorded as a plain read at the source read step. That is conservative: it can
over-report relative to a lower-level microarchitectural model, but it keeps
same-address read/write dependence visible to DPOR and avoids hiding races.

Atomic and lock happens-before rules are unchanged because they execute only
with an empty buffer.

## Independence and DPOR

The DPOR scheduler now keys enabled/backtrack/done/sleep sets by concrete
`ScheduleStep`, not only by thread id. Under TSO a thread can have both its next
source action and an internal flush enabled, so the old one-transition-per-
thread assumption would miss schedules. Same-thread source/flush alternatives
are not considered independent.

`Flush(x)` is a write-like memory transition. It is dependent with any
other-thread memory action on `x`, including another flush of `x`, because the
order changes values, race endpoints, and future happens-before observations.
It is independent of register-only actions and memory actions on different
addresses.

The existing optimality meter remains SC-only. Its Mazurkiewicz-class
canonicalizer assumes one enabled transition per thread and classifies source
actions, not internal store-buffer transitions. Extending it to TSO requires a
separate transition alphabet and class-count argument; the new `tso_oracle`
gate covers TSO soundness against the naive oracle instead.

## Consequences

Existing SC tests remain the regression bar. New TSO gates compare naive and
DPOR in TSO mode, assert replay identity for schedules containing flush
sentinels, and cover litmus outcomes such as store buffering and
store-to-load forwarding.
